PART 1

Problem & the identity layer

Why three products need one foundation instead of three separate data models.

The problem

Three teams — lifecycle/CRM, sales/concierge, and marketing — each need to know "who is this person," but each team's system resolves identity differently, or not at all. A customer who shops under a personal email, buys again from a business account, and later browses anonymously on a phone looks like three unrelated people to three unrelated systems. The result: a reactivation offer sent to someone who already converted on a different account; a sales rep who can't see a VIP customer's full purchase history because it's split across logins; a marketing audience that double-counts or drops people because match rates differ by channel.

The approach

Introduce a single identity-resolution layer beneath all three products. Every known identifier (email, phone, external user ID, device/cookie ID) resolves to one canonical Person ID. Each product reads from and writes to that same Person Graph instead of maintaining its own partial view.

Core entities
EntityPurpose
PersonThe canonical, de-duplicated individual. Has one Person ID.
IdentityOne known identifier (email, phone, external user ID) linked to a Person, with a match confidence and source.
SignalA behavioral or attribute fact about a Person (lifetime spend, consent status, suppression flag, recency).
Model ScoreA named model's output for a Person (propensity to convert, churn risk), versioned.
This mirrors how Segment's Identity Resolution (and similar CDPs) models identity graphs: probabilistic + deterministic matching collapsing many identifiers into one profile, exposed through a Profile API that downstream systems query instead of re-deriving.
PART 2

CDP: decisioning engine

Given a resolved Person, decide what action (if any) is eligible — and show the reasoning.

User stories

  • As a lifecycle marketer, I want to see whether a customer is eligible for a reactivation offer, so that I don't send offers to people who already converted or who are suppressed.
  • As a compliance stakeholder, I want every automated decision to log why it was made, so that conflicting signals (e.g. high propensity but suppressed) are auditable, not silent.
  • As a PM, I want the eligibility rules to be explicit and inspectable (not a black-box model call), so non-engineers can review and adjust thresholds.

Decision logic (reactivation offer example)

Rule: reactivation_eligibility_v1
  1. If suppressed = 1, result is suppressed regardless of model score — suppression always overrides.
  2. Else if propensity_to_convert > 0.70 AND marketing_consent = 1, result is eligible.
  3. Else result is not eligible, with the specific reason (low propensity, no consent) recorded.

Every evaluation is persisted as a Decision record with the action, result, human-readable reason, the model/version used, which rule fired, and whether a conflict was detected (e.g. a high-propensity person who is also suppressed) — this is the audit trail compliance and marketing ops both need.

PART 3

Identity API contract

The interface every downstream product (Rep App, Marketing) consumes instead of building its own resolution logic.

GET /identity/lookup

GET /identity/lookup?identifier=jordyn@personalmail.com

200 OK
{
  "person_id": "PER-4471",
  "identities": [
    { "email": "jordyn@personalmail.com", "account_type": "personal",
      "match_confidence": 0.94, "source": "segment" },
    { "email": "jordyn@resellerco.com",   "account_type": "business",
      "match_confidence": 0.94, "source": "segment" },
    { "phone": "+1-206-555-0111",         "account_type": "anonymous",
      "match_confidence": 0.71, "source": "segment" }
  ],
  "match_confidence": 0.71,
  "source": "segment",
  "last_updated": "2026-01-14T18:22:00Z"
}

Design notes

  • identifier accepts email, phone, or external user ID — the resolver tries each identity type.
  • match_confidence on the response is the lowest confidence among linked identities, so a low-confidence anonymous link visibly drags down the overall score rather than being hidden by an average.
  • 404 (not 200 with an empty body) when no person resolves — callers should treat "unknown identifier" as a distinct case from "known person, no identities," which shouldn't happen but is handled explicitly.
  • The resolver is swappable behind one interface (IdentityResolver): a mock/seeded implementation for demos and a real Segment Profile API implementation for production, selected by config, not by call-site branching.
PART 4

Rep App requirements

Give a sales/concierge rep one unified view of a customer, built on the same Person ID — no more hunting across three systems mid-call.

User stories

  • As a sales rep, I want to search a customer by name, email, or phone and get one profile back, even if they've shopped under more than one account, so I don't miss purchase history or give a VIP customer a generic experience.
  • As a rep, I want a suggested talking point based on the customer's recent activity and model scores (e.g. "high churn risk — consider early check-in"), so I don't have to interpret raw data mid-conversation.
  • As a support lead, I want an escalations view showing customers with open issues flagged by signals (e.g. recent negative activity), so reps can prioritize outreach.

Requirements

#RequirementPriority
R1Search accepts partial name, full email, or phone; resolves through the Identity API, not a separate customer database.P0
R2Unified profile shows all linked identities (personal/business/anonymous) with confidence, so the rep knows how certain the match is.P0
R3Profile surfaces lifetime value, recent activity timeline, and current model scores (propensity, churn risk) in plain language, not raw numbers only.P1
R4A generated "talking point" string combining the top signal and score into one sentence a rep can use live.P1
R5Escalations view lists customers matching a risk/complaint rule, refreshed on load.P2
PART 5

Marketing Intelligence requirements

Let marketing build an audience from the same resolved signals and scores, preview its size, and push it to a channel — without exporting CSVs between teams.

User stories

  • As a marketer, I want to build an audience by combining signal/score conditions (e.g. propensity > 0.7 AND not suppressed), so I can target without engineering help.
  • As a marketer, I want to preview the matched count before syncing, so I can sanity-check an audience before it goes live in a channel.
  • As a marketer, I want to push an audience to an ad or email channel and see how many records actually matched (match rate), so I understand real reach, not just the raw list size.
  • As a marketing ops lead, I want a library of saved audiences with their last sync status, so I can reuse and audit what's live.

Requirements

#RequirementPriority
M1Audience builder supports ANDed conditions over any Signal or Model Score field with standard operators (>, <, >=, <=, =, !=).P0
M2Preview returns a matched count and a small sample of Person IDs before saving/syncing.P0
M3Sync to a named channel (Meta, Google, ESP) returns a match rate (matched vs. total), mirroring real hashed-identifier match behavior rather than assuming 100%.P1
M4Audience library lists saved audiences with name, rule, and last sync status/timestamp.P1
M5OR logic and nested condition groups.P2 — not in current prototype
PART 6

Measurement & reporting

Close the loop: once an audience is synced to a channel, bring its performance back into Smart Engine instead of leaving it siloed in each platform's own dashboard.

User stories

  • As a marketer, I want to see how an audience performed after I synced it — impressions, clicks, spend, conversions, ROAS — without opening Meta Ads Manager, Google Ads, and the ESP separately and reconciling three different numbers.
  • As a marketer, I want performance broken out by channel, so I know which channel is actually driving results for a given audience rather than looking at one blended number.
  • As a PM or marketing lead, I want a trend over time, not just a lifetime total, so I can see whether a campaign is accelerating, flat, or fading.

Why this lives here instead of in each channel's own dashboard

Meta Ads Manager and Google Analytics already report on performance — but only for that one channel, and only in terms of their own campaign IDs, not the Person IDs this platform already resolved. The thing a platform-native dashboard can't do is tie a Meta impression and an email open back to the same Person ID the identity layer resolved in Part 1, or report on performance for an audience that was synced to more than one channel at once. That's the gap this part fills: not a replacement for Meta/Google's own reporting, but one rollup, keyed to Smart Engine's own audiences, that those platforms can't produce on their own.

Requirements

#RequirementPriority
MS1Every channel sync is measurable: once an audience is synced, performance data starts flowing without any extra setup step.P0
MS2A performance summary per audience: total impressions, clicks, spend, conversions, revenue, and the derived rates (CTR, CPA, ROAS) that marketers actually make decisions on, not just raw counts.P0
MS3A daily trend, not just a lifetime total — spend and revenue over time at minimum, so a campaign's trajectory is visible, not just its cumulative result.P0
MS4A per-channel breakdown when an audience is synced to more than one channel, so performance isn't blended into one number that hides which channel is actually working.P1
MS5Metrics refresh on a schedule from each channel's own reporting API (a real provider), not a one-time snapshot — platforms commonly revise same-day numbers for 24-72 hours after the fact.P2 — mocked in current prototype
MS6Attribution back to the Person ID: which specific resolved people converted, not just an aggregate count — the thing a channel-native dashboard structurally can't do.P2 — not in current prototype
GET /audience/{id}/performance — current prototype

Returns a summary (impressions, clicks, spend, conversions, revenue, CTR, CPA, ROAS), a per-channel breakdown, and a daily timeseries, aggregated across every channel the audience has been synced to. In this prototype, a MockMetricsProvider generates a realistic 14-day performance curve immediately after a sync — the same swappable-provider pattern as identity resolution (Part 3): a real deployment implements MetaInsightsProvider/a Google Ads equivalent against each channel's actual reporting API without touching any other code.

PART 7

Roadmap

Three phases from reference implementation to production-ready platform.

PHASE 1

Reference implementation

  • Identity, decision, audience, and measurement engines as a working API (this prototype)
  • Mock resolver and mock metrics provider with seeded demo data
  • Three-app frontend wired to live endpoints
PHASE 2

Real integration

  • Swap mock resolver for a real Segment (or equivalent CDP) Profile API connection
  • Real channel sync (Meta Conversions API, Google Customer Match, ESP)
  • Real measurement pull from each channel's reporting API, replacing the mock metrics provider
  • Auth, multi-tenancy, and role-based access for reps vs. marketers vs. admins
PHASE 3

Scale & governance

  • OR logic / nested audience rules
  • Decision rule management UI (no-code threshold editing)
  • Consent and suppression sync back to source systems
  • Usage-based billing and customer-facing admin console
This is a portfolio prototype, not a production system: no authentication, no multi-tenancy, no real channel integrations yet. The underlying identity-resolution and decisioning patterns are based on real industry practice (Segment-style Identity Resolution, customer-360 PRDs) but all naming, schema, and sample data here have been generalized and are not tied to any employer's proprietary system.
